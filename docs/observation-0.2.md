# 0.2.0 观察可靠性改动

背景：一次真实 App 自测的使用记录（196 个执行计划、419 个动作，单个计划耗时中位数约 2.69 秒）暴露了几处观察问题。那组数字只是使用记录，不是性能基准；计划 `ok` 也不等于业务成功。本次没有做前后对照实验，不宣称提速。

## 问题核对（改动前的 0.1.0，提交 aad8c33）

| 问题 | 0.1.0 状态 | 本次处理 |
|---|---|---|
| 提交步骤只用 `expect.foreground` 也报 ok | 存在 | 报告验证强度并警告；可选严格模式 |
| 冷启动时 AX 暂无有效屏幕尺寸，报 `bad_snapshot` | 存在：立即失败，等待中也不检查暂停 | 有上限的只读等待，响应暂停 |
| 无效 AX 被当成 `gone` 成立 | 已修复（已有回归测试） | 保持；新增持续无效时的回归 |
| 转场时新旧页面同时出现、结果一闪而过 | 存在：条件第一次满足就返回 | 可选 `stable_ms` 和条件数组 |
| 摘要固定截取前 40 个元素 | 存在 | 按证据优先排序，屏幕外单独分组，如实标出截断 |
| 用 helper 健康证明用户能看到镜像 | 部分存在：`doctor` 只报告 helper 是否存在 | 分层报告；客户端画面固定为 unknown |
| 计划把“回首页”写成“回订单列表”导致超时 | 调用方计划错误 | 不放宽验证 |

## 兼容性

- **旧计划不需要修改**。新参数 `stable_ms`、`ax_ready_ms`、`strict_commit` 和条件数组都是可选的。
- **仅前台或仅 `gone` 的提交**：默认照常执行，状态不变，但新增 `commit.verification` 和 `warnings`。设 `"strict_commit": true` 后，执行前就被拒绝（退出码 2）。
- **冷启动**：原来遇到无效快照会立即失败，现在最多只读等待 `ax_ready_ms`（默认 5 秒）。只针对“缺少有效屏幕尺寸”这一种情况；HTTP 错误、连接断开等仍立即失败。
- **暂停**：原来只在步骤之间和定位时检查，现在等待条件、等待有效快照时也会检查。动作已发出后才暂停的，`error.action_sent` 为 true，`stopped_before` 指向下一步；提交步骤这种情况报 `unknown`。
- **摘要输出**：`final.elements` 仍是字符串数组，但现在只含屏幕内元素，并重新排序。新增 `offscreen`、`matched`、`omitted` 字段。如果有脚本依赖旧的元素顺序或在 `elements` 里找屏幕外元素，需要改读 `offscreen`。
- **`doctor --udid`**：`device.helper` 从 `{pid,url}` 或 `null` 改为 `{state, pid?, url?}`；新增 `ax` 和 `client_view` 字段。
- 新增结果字段：`ax_invalid_reads`、每步的 `observed`，以及提交步骤的 `commit`。

## 离线回归（`npm test`，40 项全部通过）

新增 `tests/observation.test.mjs`：

1. 冷启动有 3 次无效快照，之后恢复：点击只执行 1 次。
2. 快照持续无效：有上限地失败、不点击，`gone` 不会被判为成立；等待中能暂停。
3. 提交后 AX 读取失败、点击中连接断开、提交后快照变为无效：都报 `unknown`，只发 1 次。
4. 转场时结果闪现后又消失：不提前判定成功；始终不稳定时报 `unstable_result`，提交步骤报 `unknown`。
5. 结果出现、指定的加载遮罩消失：在第一次同时满足时立即返回，没有固定等待。
6. 时钟和无关动画在变：不影响相关条件完成。
7. 仅前台的提交：默认警告；严格模式在任何输入前拒绝；`presence` 提交没有警告。
8. 动作发出后在等待中暂停：报告 `action_sent`。暂停、占用冲突和释放的原有测试全部仍通过。
9. 长 AX 树末尾的关键结果：排在摘要第一位，同时如实标出截断和屏幕外元素数量。

## 实机小范围验证

环境：一台临时新建的 iPhone 17 / iOS 27.0 模拟器，Xcode 27.0，serve-sim 0.1.48，只操作系统“设置”App。测试结束后，设备已删除，临时状态目录也由退出清理删除。

| 检查 | 结果 |
|---|---|
| `doctor --udid` 分层 | helper healthy，ax readable（新开机的设备第一次读界面约 5 秒），client_view unknown，占用方正确 |
| 冷启动后立即执行“通用 → 关于本机”（`stable_ms: 300`，最后一步要求标题“通用”已消失） | 3/3 成功。第 3 次遇到 1 次无效快照，等待后继续。0.1.0 会直接失败 |
| 稳定观察 | 每步都记录了实际稳定时长（0.55–1.57 秒）；摘要第一行就是命中的“iOS 版本”行，`matched` 正确 |
| 终态截图 | 3 次都在终态观察之后截取 |
| 仅前台的提交（在“设置”里无害地点一下） | 默认：`ok`，`verification: foreground_only`，带警告。严格模式：执行前拒绝，退出码 2 |
| 等待中暂停 | 在 `stable_ms` 等待期间暂停，状态 `paused`，一个动作都没执行 |
| 释放 | 自己启动的 helper 已停止并核实退出；用户的暂停在释放后仍保留 |

## 尚未验证

- 真实业务 App、App 内 WebView/H5、自定义加载遮罩的命名方式。
- 屏幕外元素判断只用元素中心是否在屏幕内，没有处理遮挡或滚动容器裁剪。
- 弹窗/HUD 类元素的识别靠类型名关键词，不同 App 的命名可能不在列表里；遇到这种情况请把它写成明确的条件。
- 与 Codex 预览服务器真实共存；客户端是否真的显示画面，本脚本仍无法判断。
- 本次没有测量对整体耗时的影响。

## 发布前摘要修正

- 摘要与条件判断采用相同的 `nth` 序号，避免把其他同名元素当成命中证据。
- `matched` 最多返回 `summary_limit` 条，增加匹配总数与省略数；不会绕过摘要限制输出整棵树。
- `run` 的屏幕外摘要默认保留 10 条；独立读取 `ax --limit N` 时，屏幕内和屏幕外两组各最多 N 条，可按需扩大范围。
- 上述三处新增离线回归，本轮未重新运行模拟器，前面的模拟器记录仍为原作者验证范围。
